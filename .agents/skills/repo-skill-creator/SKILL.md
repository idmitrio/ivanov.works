# Repository Skill Creator

## Purpose

Use the built-in skill-authoring guidance for generic design and writing. This skill adds only repository rules for deciding ownership, placing files, protecting managed copies, and validating the result.

Read the target repository's `AGENTS.md` before editing.

## Ownership Decision

All repo-scoped skills live at `.agents/skills/<name>/`; ownership is determined by repository and marker, not by a different path.

- In `codex-shared-skills`, every new skill is a canonical shared skill. Do not create unmanaged local skills or overlays in this repository.
- In any other project, a skill without `.codex-shared-skill.json` may be created as an unmanaged project-local skill.
- A local overlay is an unmanaged local skill that adds project-specific behavior around a shared skill. If `codex-skills.json` exists, map the shared skill name to `.agents/skills/<overlay>/SKILL.md` in `local_overrides`.
- A target-project copy is managed only when `.codex-shared-skill.json` is valid JSON, `schema_version` is `1`, `managed_by` is `codex-shared-skills`, and `skill` equals the directory basename.

Never edit a valid managed copy in a target project. Change the canonical skill in `codex-shared-skills`, then update the target through `scripts/codex-skills.sh`. An absent, invalid, or mismatched marker grants no overwrite or delete authority.

The canonical marker shape is:

```json
{"schema_version":1,"managed_by":"codex-shared-skills","skill":"example-skill"}
```

Extra updater fields may exist, but they do not relax the two ownership checks above.

## Placement And Naming

- Create every skill as a direct child of `.agents/skills/`; do not create `managed/`, `local/`, or `overlays/` subtrees.
- Use one lowercase hyphenated name per folder, with `SKILL.md` inside it.
- Keep project-specific behavior out of canonical shared skills; use a target-project local skill or overlay.
- Do not place skill files under `docs/` or register skills in `AGENTS.md` for discovery. Codex discovers `.agents/skills/` automatically.
- Mention a skill in `AGENTS.md` only when a real repository routing or safety rule needs it.

## Required Repository Files

Canonical shared skills require:

```text
.agents/skills/<name>/
  SKILL.md
  skill-manifest.json
  agents/openai.yaml
```

Add self-contained `references/`, `scripts/`, or `assets/` only when needed. Do not include secrets, machine-local absolute paths, caches, vendors, generated bytecode, or temporary files.

`skill-manifest.json` must use schema version `1` and list only mandatory shared-skill dependencies:

```json
{"schema_version":1,"requires":["another-shared-skill"]}
```

Do not infer dependencies from prose or declare shared-skill relationships in `agents/openai.yaml.dependencies`.

Unmanaged local skills in target projects must have `SKILL.md` and no managed marker. Add `agents/openai.yaml` when the skill should expose interface metadata. Do not create `skill-manifest.json` for an unmanaged local skill; manifests belong to canonical shared skills and their managed target-project copies.

## Canonical Shared Skill Contract

When working inside `codex-shared-skills`:

- read the repository `AGENTS.md` and preserve the self-contained skill folder layout;
- keep every canonical skill's `SKILL.md`, `skill-manifest.json`, and normally `agents/openai.yaml` together;
- keep helper scripts, references, assets, and templates inside the owning skill folder;
- preserve executable bits on helper scripts;
- declare dependency edges only through exact names in `skill-manifest.json.requires`;
- link another shared skill from prose with its name as visible text and a relative path to its `SKILL.md`;
- update the README shared-skill list when adding, renaming, or removing a canonical skill, and verify it against updater `list` output;
- run the full repository validator because a single manifest change can affect the global dependency graph.

The updater copies the complete canonical folder, so canonical content must not contain project secrets, customer identifiers, private hostnames, or machine-local absolute paths. Project-specific facts belong in an unmanaged target-project skill or overlay.

## Target-Project Local Skills

Outside `codex-shared-skills`, a local unmanaged skill uses the same discovery path:

```text
.agents/skills/local-release-rules/
  SKILL.md
  agents/openai.yaml
```

It must not contain `.codex-shared-skill.json`. Do not add it to `codex-skills.json.skills`, which selects managed shared skills.

For an overlay, connect the shared skill to the local file when `codex-skills.json` exists:

```json
{
  "local_overrides": {
    "release-workflow": ".agents/skills/local-release-rules/SKILL.md"
  }
}
```

The shared key must identify a selected or resolved shared skill, and the target must exist as a flat repository-relative `.agents/skills/<overlay>/SKILL.md` path. The overlay remains unmanaged and is discovered automatically; no `AGENTS.md` registry entry is needed.

## Metadata

Canonical shared skills normally include:

```yaml
interface:
  display_name: "Human-readable name"
  short_description: "Front-loaded, distinct action description."
  default_prompt: "Use this skill to perform a concrete repository task."
```

Keep descriptions short and distinguish nearby skills by their first words. Keep default prompts concrete. See [references/openai_yaml.md](references/openai_yaml.md) for field details.

Generate metadata when useful:

```bash
python3 .agents/skills/repo-skill-creator/scripts/generate_openai_yaml.py .agents/skills/<name> \
  --interface display_name="Example Workflow" \
  --interface short_description="Create example repository workflows." \
  --interface default_prompt="Use this skill to create or update the repository's example workflow."
```

## Workflow

1. Locate the repository root and classify the skill as canonical shared, unmanaged local, or local overlay.
2. Inspect the destination and marker before any write. Stop on a same-name unmanaged/managed collision instead of replacing content.
3. Use the built-in authoring guidance to design the skill; apply the ownership, layout, metadata, and dependency rules above.
4. Create or update `.agents/skills/<name>/`.
5. For an overlay, update `codex-skills.json.local_overrides` when that file exists; never put the overlay name in the managed `skills` array.
6. Update references, manifests, commands, prompts, examples, and metadata affected by a rename.
7. Validate links and the skill. In this canonical repository, run the full validator and relevant tests.
8. In a target project, refresh managed copies only through updater preview and apply.

## Rename Checklist

A rename changes repository identity, not only a folder name. Update:

- the directory basename and frontmatter `name`;
- Markdown links and visible link text;
- validator/generator command paths;
- `skill-manifest.json` dependency names in other skills;
- `codex-skills.json` examples, prompts, and updater selections;
- `agents/openai.yaml` display text and default prompt when the old identity appears.

Search hidden files and verify that the old standalone name is gone. Do not rewrite unrelated prose merely because it contains a similar substring.

After a canonical rename, report that consuming projects must update the selected name when they selected it directly, then run updater preview/apply. Do not attempt to patch every target repository implicitly.

## Upstream Update Contract

For a managed target-project skill:

1. Record the requested change and find the canonical shared repository.
2. Change the canonical `.agents/skills/<name>/` files.
3. Validate the shared repository.
4. In the target project, run:

```sh
./scripts/codex-skills.sh sync --dry-run
./scripts/codex-skills.sh sync --apply
./scripts/codex-skills.sh validate
```

Do not manually patch the copied target directory, even for a small fix.

## Validation

Validate one canonical skill:

```bash
python3 .agents/skills/repo-skill-creator/scripts/quick_validate.py .agents/skills/<name>
```

For a single target-project skill, the validator checks `skill-manifest.json`
only for managed copies marked by `.codex-shared-skill.json`. It does not inspect
a manifest in an unmanaged local skill. Canonical repository validation through
`--all` always requires and checks manifests.

Run the one canonical repository check, including skill metadata, links, registry, scripts, generator roundtrip, and E2E tests:

```bash
./scripts/codex-skills.sh check
```

Also run repository link checks and tests relevant to changed scripts. A rename is incomplete while the old name remains in Markdown links, commands, manifests, prompts, examples, or `agents/openai.yaml`.

## Stop Conditions

Stop before writes when:

- a target destination is unmanaged and would be replaced by a shared skill;
- legacy `skills/<name>` and `.agents/skills/<name>` both exist;
- a marker is invalid or does not match the directory;
- ownership cannot be determined safely;
- a canonical dependency is missing or cyclic.

Report the collision and safe options. Do not delete, merge, or assume ownership.

## Completion Criteria

- Ownership and destination were determined before writes.
- Canonical shared skills contain required manifest and metadata files.
- Local unmanaged skills have no managed marker; overlays are mapped when applicable.
- Every rename reference is consistent.
- Validator, link checks, and relevant repository tests pass.
